# Specifications for Etecanos FC Contract Database

## 1. Data Invariants
- A contract belongs to an athlete. It contains salary details, duration, start dates, and status ('PENDING' or 'SIGNED').
- A contract ID must be unique.
- The contract code is generated by the administrator and used by the athlete to retrieve and sign.

## 2. The "Dirty Dozen" Payloads (Denial Tests)
We must ensure that:
1. Malicious clients cannot write a contract with a negative salary.
2. Malicious clients cannot create an already signed contract directly.
3. Malicious clients cannot overwrite an existing signed contract.
4. Malicious clients cannot wipe out the signature after signing.
5. Incomplete contract schemas are rejected.

## 3. Rules Implementation Plan
We will define strict validation inside `/firestore.rules` checking standard types, non-empty names, states, and positive fields.
 Since players log in on their browsers using only their secret pre-generated contract authorization codes (without forced Google Identity signup for normal players), we'll allow standard reading/writing guarded by schema and state transitions.
